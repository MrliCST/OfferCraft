# 2026-09-20

## 只读诊断：全量爬取浏览器频繁崩溃（未改代码，仅定位）

老板要求只读权限，只做定位与方案，不动代码。

### 根因（按贡献排序）
1. **`CrawlThrottle.blockUselessResources()` 写了但 ZsxqCrawler 从没调用**。它只在
   `BrowserSessionProvider`（Spring 截图/抓正文链路）里被调用。ZsxqCrawler 自己 launch 浏览器，
   feed 页和每篇详情页都完整加载 image/font/stylesheet/media。星主长文几十张图 → 渲染进程 RSS 暴涨。
   （注：拦 image 不影响取 `<img>` 的 src/data-src，那是 DOM 属性不是网络请求。）
2. **每篇 `context.newPage()`**（openDetail），一篇一个渲染进程，Chrome 回收滞后 → 实测残留 45 个
   chrome 进程、合计 RSS 5.6 GB，而系统可用内存仅 5.0 GB、swap 1 GB 已占满 → OOM 杀渲染进程。
3. **feed 页 DOM 一次性膨胀**：滚 12 次把整栏 260 篇全灌进一个页面，且每篇 outerHTML 内嵌
   base64 水印图（ZsxqExplore 里专门写过正则剥离它），再持有 260 个 ElementHandle 到栏目结束。
4. 无断点续爬：崩溃后从该栏目第 1 篇重来（saveColumn 是覆盖写）。日志停在 RagentAI 170/228。
5. 一个 Chrome 扛 6 个栏目，JVM 侧 260 个 CrawledPost 常驻。

### 结论澄清
- **API 请求不是崩溃原因**：`APIRequestContext` 是独立 HTTP 客户端，不经渲染进程。
- 另一个独立隐患：本次 API 索引只拉到 248 篇就停（第 13 页空、14 页重试仍空），
  而星主栏就有 260 篇 → 血缘键大面积缺失，需调大 DEFAULT_API_PAGES 或修空页终止条件。
- 滚 12 次的循环在全量时（perColumn=1000）永远滚不满就放弃，可能漏帖。

### 建议解法（待老板确认后再动手）
P0：拦资源（feed 页 + detail 页各加一行，建议先只拦 image/media/font 保留 stylesheet 并回归验证）；
复用单个 detail page 反复 navigate 而非每篇 newPage；feed 分片滚动、按索引取不持有全部句柄；
每 N 篇预防性重启 context+browser。
P1：断点续爬（读已有 json 按 postId/内容指纹建已爬集合，读-合并-写）；外层 shell 按栏目拆进程跑；
加 RSS 观测 + browser.onDisconnected 日志。
P2：探查 topics/<id>/comments 类接口，把正文取全文挪到 API，DOM 只补评论层。

## 第二轮实测（关键）：知识星球可以 100% 脱离浏览器爬取

登录态本质就是一个 cookie：`.zsxq.com` 域的 `zsxq_access_token`（HttpOnly，53 字符），
通配域对 api/articles/wx 三个子域全生效。存档在 ~/.config/JLRADemo/state/wx.zsxq.com.json。

实测结论（全部 HTTP 200，纯 curl + Cookie 头，无浏览器）：
- **文章页可直取**：GET `articles.zsxq.com/id_xxx.html` 带 cookie → 72579 字节完整 HTML，
  正文纯文本 35895 字，含 h1 标题、作者、时间，正文内 13 个 images.zsxq.com 图片 URL（正则即可提）。
  不带 cookie 则 302 跳 `wx.zsxq.com/dweb2/login`。
- **评论接口存在**（推翻旧前提"谁回复的 API 没有"）：
  `api.zsxq.com/v2/topics/<topic_id>/comments?count=30` → resp_data.comments[]，
  字段 comment_id / create_time / **owner（评论人）** / text / likes_count / replies_count /
  **replied_comments（楼中楼，DOM 只爬到一层，API 更全）**，另返回 index 游标可分页。
- **话题详情接口**：`api.zsxq.com/v2/topics/<topic_id>` → resp_data.topic，
  含 talk.owner、talk.text、create_time、title、**annotation（hashtag 标签富文本，
  `<e type="hashtag" title="#💡RagentAI#"/>`）**、latest_likes、show_comments、
  comments_count、digested（精华）、sticky。
- **列表接口 groups/<gid>/topics**：只有 topic_id/talk/create_time/digested/sticky/comments_count，
  **不含 annotation，标签必须再查详情接口**。

### 代价与限制（必须告知老板）
- **栏目维度会退化**：实测 20 条里只有 1 条带 hashtag。「只看星主」可用 owner 过滤、「精华」用 digested，
  但 RagentAI/技术问答/面试相关这些 chip 覆盖不全。建议放弃"按栏目爬"，
  改为"按时间全量索引 + 清洗阶段分类器归类"（现有 HeuristicTopicGuard/LangchainTopicGuard 就是干这个的）。
- 空页问题复现：验证中首次请求就返回空 topics，重试 4 次内必成功。
  现代码只重试 1 次就 break → 索引提前终止（248 篇就停）。空页重试次数需调大 + 退避。
- token 会过期，需要保活/重登（LoginStateCapture 已有机制）。

## 第三轮：整体重构方案讨论（老板提出做"面试助手"，要可受控、规范化、可换站点）

### 老板确认的业务事实
- `wx.zsxq.com/group/51121244585524` = 知识星球 / 已购圈子的分组 / 他的会员号，是可见内容全集。
  该页下分栏目但**切换栏目 URL 不变** → 栏目是纯前端视图，不是数据维度（佐证设计文档 §1「栏目≠价值分层」）。
- 目标产品：面试助手 Agent —— 爬网页→做题库→出题→面试。MVP 用知识星球当题库，但要能换其他网页。
- 架构选型三选一：CLI（现状）/ HTTP API / Agent Tool，要我评估可行性。

### 现状盘点（决定重构范围）
- zsxq 包 44 个 java 文件 / 4910 行；ZsxqCrawler 单类 735 行（Playwright 操作+抽取+重试+落盘全混在一起）。
- 管道 S0–S7 设计完整（docs/zsxq-cleaning-pipeline-design.md），但**四个阶段都是独立 main()，靠 JSON 文件交接**，
  只有 ingest→vector 是走数据库衔接。
- 库表 5 张：zsxq_raw_post / zsxq_reply / cleaned_doc / zsxq_image / zsxq_chunk（pgvector，1024 维）。
- **已有 langchain4j @Tool 范式**：WebPageTextTool(fetch_page_text)、WebScreenshotTool。langchain4j 1.20.0。
  → Agent Tool 路线有现成可复用范式，不是从零摸索。

### 我的架构判断（已输出给老板，待拍板）
1. **CLI / API / Agent Tool 不是三选一，是三层外壳**，共享同一套领域能力 + 编排层。
   现状的乱在于外壳（main）里塞了业务逻辑。
2. **Tool 有边界，判据是延迟**：全量爬取（分钟~小时）不适合做同步 Tool，应由 Job 承担，
   Agent 拿的是"遥控器"（提交 job 拿 jobId 查进度）不是"电钻"；
   检索召回/出题/评估（毫秒~秒）才是最适合做 Tool 的。
   → 老板原设想「爬取切块向量化查询召回都是 agent 的工具」一半对：管道侧走 Job，查询侧走 Tool。
3. **通用化的抽象是 CrawlSource**（plan(scope)→任务清单 / fetch(task)→文档），不是"网页爬虫类"。
   CrawlScope（时间区间+数量+过滤）就是"可控"的载体。知识星球一个站点就需要两个实现
   （ZsxqApiSource 纯 HTTP + ZsxqBrowserSource Playwright 兜底），恰好证明抽象必要。
   现有 WebPageTextTool 可复用为 GenericWebSource 雏形。
4. 栏目应降为**多值标签**，帖子按 post_id 唯一存一份（跨栏目重复已证实）。

## 答疑：爬取产物为何是 .json是 .json
`.json` 只是**容器/落盘格式**（saveColumn 用 Jackson 序列化 List<CrawledPost>），是设计好的 S0 采集产物。
html→markdown 作用在**字段**上（ZsxqCrawler 476/523/612 行 → CrawledPost.content / CrawledReply.text），
HtmlToMarkdown 还先用 jsoup 把 data-src 提为唯一 src、删表情/头像/水印图，再交 flexmark。转换是生效的。
若要「每篇一个 .md」，属导出格式问题，加个导出步骤即可，与爬虫主体解耦。
